## Что уже хорошо

Основной системный промпт текста соответствует позиционированию ABBiO: путь спрос → сайт → обращение → CRM → продажа → аналитика, аудитория руководителей, практические объяснения и спокойная подача. Есть явный запрет придумывать статистику, результаты клиентов и кейсы; условные примеры должны отличаться от реальных. Эти требования сохранить.

Промпт изображения связан с конкретной темой и статьёй, задаёт тёмный графитовый фон, сдержанный violet/lavender, чистую композицию, отсутствие текста/логотипов/лишних людей. Тематические примеры не объявлены единственным обязательным сюжетом. Эта часть в основном соответствует сайту.

## Несоответствия, которые мешают запуску

1. **Модуль 19 отправляет материал на другой сайт.** Он использует старый multipart-контракт с HASH_KEY. Для ABBiO нужны отдельные запросы upload → JSON create draft → publish, Bearer-токен сайта и Idempotency-Key. Изменить только домен недостаточно.
2. **Модуль 22 требует HTML вместо Markdown.** Системный промпт прямо запрещает Markdown, разрешает HTML с H4 и таблицами border/caption. API ABBiO отклонит сырой HTML; шаблон принимает H2/H3, GFM, ограниченные callout/CTA. Нужно согласовать формат генерации с API, убрать старую HTML-секцию.
3. **В модуле 22 остался другой заказчик.** Пользовательское сообщение «Напиши статью для компании ОборонСпецСплав» конфликтует с системным контекстом ABBiO. Убрать остаток и передавать тему/редакционный бриф ABBiO.
4. **Модуль 9 остался для мотошколы/Дзена.** Он создаёт кликбейтный заголовок и привязан к другой аудитории. Для сайта нужен точный заголовок, отвечающий поисковому намерению и стилю основного текста.
5. **Нет обязательных полей нового API.** Сейчас собираются NAME и DETAIL_TEXT, но не slug, description, excerpt, category. Нужны строгое JSON-представление/парсинг и проверка значений. Одна категория из websites/marketing/seo/analytics/practice; дополнительные темы — tags. Связанные услуги/кейсы брать из существующих slug сайта, реальные факты — только из предоставленного брифа.
6. **Неверно объединены схемы ответа изображений.** PREVIEW_PICTURE берётся из `16.data.data[].b64_json`, DETAIL_PICTURE — из `16.data.choices[].message.images[].image_url.url`. Второй путь относится к другой форме ответа. По документации текущего Images API изображение находится в `data[].b64_json`; media_type может отсутствовать для PNG. Сейчас сборка data URI тогда может дать пустой MIME. Нужны выбор одного результата, проверка b64, декодирование в бинарный файл и отдельный upload ABBiO, который возвращает `/media/articles/<uuid>.webp`.
7. **Модуль 11 генерирует имя файла, а не описание изображения.** Он видит тему, но не готовую обложку. Для coverAlt нужно содержательное описание визуального сюжета, соответствующее изображению; имя файла сайту назначает upload endpoint. Формировать alt из визуального брифа и проверить соответствие готовой картинке.
8. **Очередь заканчивается удалением темы.** Вместо истории статусов/ID статья исчезает из Airtable после HTTP-запроса. При неопределённом результате или повторном запуске нет article ID, revision и стабильных ключей операций. Смена delete на update статуса с сохранением ID/revision/URL и результатов этапов позволит продолжать незавершённую операцию.

## Надёжность и качество: рекомендации

- Сохранять articleId/revision и ключи upload/create/publish в записи очереди или Make Data Store до повторов. Idempotency-Key создавать один раз на операцию, сохранять при её повторе, менять для нового изменения. После таймаута publish повторять ту же операцию, а не генерировать статью заново.
- Разделить статусы очереди, например new → processing → draft_ready → published/error; это предложение, не утверждённая схема Airtable. Проверить view-фильтр, резервирование записи и последовательную обработку, чтобы два выполнения не выбрали одну тему. Make сейчас получает только поле темы; для практических кейсов нужны подтверждённый бриф, источник и период результатов.
- В модуле 19 включить parseResponse для нового API, проверять ID/revision/status. При 409 читать актуальную редакцию и разбирать конфликт; при 422 исправлять входные данные; 503/сетевой таймаут повторять с тем же ключом. Не удалять входной материал при ошибке.
- Сохранять готовый Markdown, метаданные и результат изображения до публикации. При сбое доставки повторные генерации будут расходовать ресурсы и менять содержание. Добавить обработчики ошибок/неполных выполнений с ограниченными повторами.
- В модуле 16 JSON собирается строкой с `"prompt": "{{5.result}}"`. Проверить экранирование кавычек и переводов строки; предпочтительнее штатный JSON builder/структура. Это риск текущей сборки тела, а не установленная ошибка реального запуска.
- Ограничение «минимум 7000 знаков» может растягивать узкие темы; полезнее требовать достаточное раскрытие без повторов. Большие повторяющиеся стилевые инструкции можно сократить, сохранив запрет выдумок и конкретные требования к результату. Четыре LLM-вызова можно пересмотреть: article/title/meta в одном структурированном результате, отдельный image prompt/alt. Это предложение по упрощению, не требование переписать всё.
- В текущем сценарии нет источникового поиска, проверки фактов или редакционного согласования. Формулировки промпта «учитывай современные требования» не подтверждают актуальность фактов. Для публикаций про меняющиеся правила/функции нужны переданные первичные источники либо отдельная проверка; для общих объяснений не придумывать даты и цифры.
- `confidential=false`; обычные журналы выполнения могут содержать текст и base64. Не выводить Authorization, ключи и большие изображения в свои журналы/отчёты; оценить режим хранения журналов под реальный процесс.

## Предлагаемая цепочка ABBiO

Выбрать и зарезервировать тему → получить Markdown и JSON-метаданные → проверить/сохранить результат → сформировать визуальный бриф/alt → создать картинку → декодировать бинарные данные → POST `/api/articles/assets` → POST `/api/articles` со status draft → сохранить articleId/revision → отдельный POST `/api/articles/<id>/publish` по выбранному правилу публикации → обновить статус Airtable и сохранить публичный URL.

При редактировании: GET рабочей версии → PATCH с expectedRevision → отдельный publish. Критерий готовности: успешный end-to-end тест с реальным материалом, проверка draft=404, publish=200/metadata/sitemap, повтор без дублей и корректное продолжение после сбоя.

API сайта пока подготовлен только локально; до запросов с Make необходимы миграция предоставленной PostgreSQL из сети хостинга и отдельная публикация версии сайта. Контракт: [MAKE-API.md](MAKE-API.md). Подключение для следующих чатов: [MAKE-CONNECTION.md](MAKE-CONNECTION.md).

Основание разбора: прочитанные детали, blueprint и журнал этого сценария; [официальный контракт Images API OpenRouter](https://openrouter.ai/docs/guides/overview/multimodal/image-generation), [Make Scenarios API](https://developers.make.com/api-documentation/api-reference/scenarios).
